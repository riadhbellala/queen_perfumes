## Supabase Schema Reference

Project: `the-queen-of-perfumes` (id/ref `gvqiiznuyjjxrctqhgty`, region eu-central-1). Full schema lives in migrations — read those for exact SQL, this is just the map.

**Tables** (`public` schema, RLS enabled on all six):
- `perfumes` — `id, name_fr, name_ar, description_fr, description_ar, price, image_url, scent_family, concentration (EDT|EDP|Parfum|Extrait), stock, is_active, created_at`. Public can `select` where `is_active = true`; `authenticated` has full access.
- `packs` — same shape as `perfumes` minus scent fields, plus `is_featured`. Same RLS pattern.
- `pack_perfumes` — join table, composite PK `(pack_id, perfume_id)`. `pack_id` cascades on delete, `perfume_id` restricts (can't delete a perfume that's still in a pack). Public `select`, `authenticated` full access. Indexed on both FK columns.
- `pack_size_pricing` — PK `size` (2-6, checked), `price`. Seeded: 2→1900, 3→2500, 4→3600, 5→4500, 6→5000 DA. This is the single source of truth — both pack builders fetch it live; `PACK_SIZE_PRICING` in `src/lib/placeholder-data.ts` is dead/unused (still has the stale 2700 for size 3, but nothing reads it).
- `orders` — guest checkout orders. `status` defaults `pending`, checked against `pending|confirmed|shipped|delivered|cancelled|refused`. No public policies at all — rows are only ever created via `place_order()`. `authenticated` can `select`/`update` (no insert/delete, even for admins — full audit trail by design).
- `order_items` — one row per cart line. Exactly one of `perfume_id`/`pack_id`/`custom_pack_*` is populated depending on `item_type` (`perfume|pack|custom_pack`); FKs `set null` on delete so removing a catalog item doesn't break order history. Same `authenticated`-only select/update policy as `orders`.

**Function**: `place_order(p_customer_name text, p_phone text, p_wilaya text, p_address text, p_note text, p_subtotal numeric, p_delivery_fee numeric, p_total numeric, p_items jsonb) returns uuid`
- `security definer`, `search_path` pinned to `public`, `execute` granted to `anon` and `authenticated` — this is the only way orders get created.
- `p_items` is a JSON array of cart lines, each shaped like: `{ item_type, perfume_id?, pack_id?, custom_pack_size?, custom_pack_perfume_ids?, quantity, unit_price, line_total }`.
- Inserts the `orders` row, inserts one `order_items` row per cart line, then decrements `perfumes.stock` — directly for `perfume` lines, via `pack_perfumes` lookup for `pack` lines, and across `custom_pack_perfume_ids` for `custom_pack` lines. Returns the new order's `id`.
- **Stock decrements are conditional, not clamped**: each decrement is `update perfumes set stock = stock - qty where id = ... and stock >= qty`; if that affects zero rows, the function `raise exception`s a message prefixed `INSUFFICIENT_STOCK:` (client code pattern-matches on this substring to show a specific "not enough stock" message rather than a generic error). Because the whole function is one implicit transaction, that exception rolls back the `orders` row and every `order_items` row/stock decrement made earlier in the same call — no partial orders, no oversold stock.
- The security advisor flags `place_order` as an anon-callable `SECURITY DEFINER` function — that's intentional (guest checkout has no auth), not a bug to fix.

**Storage**: bucket `perfume-images` (public), created by migration `create_perfume_images_bucket`. 4 policies on `storage.objects`, all scoped to `bucket_id = 'perfume-images'`: public `select`, `authenticated` `insert`/`update`/`delete`. Used by both admin Perfumes CRUD and Boxes CRUD (`src/lib/supabase/storage.ts`) — box images share this same bucket rather than getting a separate one, so despite the name it now holds both perfume and box photos.

## Recommended Boxes desktop sizing — corrected from "count ≤ 2" to "fits in one row at this breakpoint"

`src/components/shop/boxes-carousel.tsx`'s old rule ("1-2 boxes → small centered row, 3+ → carousel everywhere") only worked by coincidence for the live 2-pack case and looked cramped as soon as there was real width to fill on desktop. The rule is now genuinely per-breakpoint, not a single item-count threshold:

- **Three independent max-visible-per-row numbers**: mobile `MOBILE_MAX_VISIBLE = 2` (unchanged from the previous pass — mobile is untouched by this task on purpose), `MD_MAX_VISIBLE = 3`, `LG_MAX_VISIBLE = 4`.
- A box count can fit at one breakpoint and not another — e.g. **3 boxes**: exceeds mobile's max (2), fits `md`'s (3) → shows as a scrolling carousel on mobile only, and as one static full-width row from `md:` up, simultaneously. **4 boxes** (the live count right now): exceeds mobile's and `md`'s max, fits `lg`'s (4) → carousel on mobile *and* `md`, static row only from `lg:` up. This is implemented as two blocks that are **both always rendered**, one hidden via `md:hidden`/`lg:hidden` and the other via `hidden md:block`/`hidden lg:block` — not a JS resize listener — so there's no hydration mismatch risk and no dependency on knowing the viewport at render time; CSS alone decides which one shows at any given width, and both were confirmed present in one fresh build's HTML for the current live 4-pack case (the carousel block carrying `lg:hidden`, the static block carrying `hidden lg:block`).
- The "fits" row (`EvenBoxesRow`, same file) is a `grid` with **column count equal to the actual box count** (capped at 4, with a `max-w-*` per count — `max-w-sm` for 1, up to `max-w-6xl` for 4) so cards genuinely grow to fill that row evenly instead of sitting at a small fixed width — not `flex-1` (which would let a single box stretch edge-to-edge at full viewport width, since it's a portrait card that also gets absurdly tall). Mobile's own rendering inside `EvenBoxesRow` (`flex flex-wrap justify-center`, fixed `w-64`/`w-72` cards) is byte-for-byte the same as the previous pass — only the `md:`/`lg:` classes on that same container changed.
- Only ever exceeding **every** breakpoint's max (5+ boxes) skips the static row entirely and the carousel just runs everywhere, same as before.
- **Known minor inefficiency, not a correctness bug**: the carousel's autoplay timer keeps ticking even while its container is `display:none` at wider breakpoints (e.g. the count-4 case above `lg:`). Harmless (nothing visible happens, embla reflows correctly if the viewport later narrows back into carousel range), just not worth the extra complexity of pausing it via a resize/visibility observer for this data size.

## Performance pass — two real root causes found, not guessed

"The site feels heavy" was diagnosed, not just patched — both causes below were confirmed empirically (network trace / response timing), not assumed.

- [x] **Root cause 1 — React 19 auto-preloads every `<img>` it renders, and this app uses plain `<img>` everywhere (no `next/image`).** Confirmed by curling a fresh production build: the homepage's `<head>` contained **8** `<link rel="preload" as="image">` tags (every perfume in `homepage-box-builder.tsx`'s grid, most of it below the fold), `/parfums` had **5** (every catalog card), `/boxes` had **5**. React 19 does this automatically for any eagerly-rendered `<img>` — it has nothing to do with viewport position unless the image is marked `loading="lazy"`, which nothing in this codebase had ever set. Fixed by adding `loading="lazy"` to every `<img>` that isn't the single above-the-fold hero/detail image on its page (~20 of 24 occurrences across `product-card.tsx`, `homepage-box-builder.tsx`, `creez-votre-box-builder.tsx`, cart/order-review thumbnails, the footer/drawer logo, and the admin tables/lists). **Left eager on purpose**: the header logo, the perfume/box detail pages' single main photo, and `creez-votre-box-builder.tsx`'s Step-1 size-picker photos — all genuinely the first/only visible image on their page. **Verified**: the same curl check post-fix shows 0 preloads on the homepage and `/parfums`, and exactly 1 (the real hero image) on a perfume detail page.
- [x] **Root cause 2 — every storefront page was fully dynamic (zero caching), because of *which* Supabase client it used, not because it needed to be.** `src/lib/supabase/server.ts` calls Next's `cookies()` (needed for admin's authenticated session) — and calling `cookies()` during render is a "dynamic API" that forces the *entire page* to skip Next's render cache and hit Supabase fresh on every single request, silently ignoring any `export const revalidate`. Every storefront page (homepage, `/parfums`, `/boxes`, both detail pages, `/creez-votre-box`) was using that same client purely out of habit, despite being 100% anonymous, guest-only, read-only catalog queries with no session dependency at all. Added **`src/lib/supabase/public.ts`** — a plain `@supabase/supabase-js` client with no cookie access — and switched all of those pages to it, plus `export const revalidate = 60`. Admin pages are untouched and must stay on the cookie-based client: they rely on RLS's `authenticated` role to see/edit inactive rows, which the anon `supabasePublic` client cannot do.
  - **Verified, not assumed**: timed three consecutive requests to the same fresh-build URL — first request 703ms (cold, real Supabase round-trip), second and third ~105-110ms (served from Next's server-side render cache, **~7x faster**). This is a server-side cache, not a browser one — the HTTP response still correctly says `Cache-Control: private, no-cache` (Next deliberately disables *browser* caching for ISR pages so the *server's* revalidation stays in control), so don't go looking for cache headers to confirm this works — time the requests instead, the way this was actually checked.
  - **Real trade-off, not free**: catalog pages can now show data up to 60 seconds stale after an admin edit (a price change, a perfume going out of stock, a new box). Checkout itself is unaffected — `place_order()` and the delivery-fee lookup always read live, uncached data regardless of what any storefront page happened to cache.
- [x] **Asset cleanup.** The logo (`public/assets/logo/tqp-logo-.png`) was a 500×500 PNG at 100KB, displayed nowhere larger than 64px tall, on every single page (header + drawer + footer) — resized to 300×300 (still >4x the largest on-screen size, no visible quality loss) at 48KB, in place, no code changes needed. Removed three files that were pure dead weight in `public/`, confirmed via grep to have zero references anywhere in `src/`: two design-reference screenshots the user had shared for me to look at (968KB, 2.4MB — never meant to be permanent site assets) and an unused mobile-hero image variant (`tpq-mbile.webp`, 112KB) that nothing ever ended up wiring up.
